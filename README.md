# 🧠 Lead Classification Model

**🔴 Live Demo:** [lead-classification-model-tjzqwfxkdlobbizyrjyhxd.streamlit.app](https://lead-classification-model-tjzqwfxkdlobbizyrjyhxd.streamlit.app)

A machine learning classification system that predicts restaurant lead priority (**High / Medium / Low**) using a **Random Forest classifier**, trained on real-world business lead data. The project covers the full ML lifecycle from raw data cleaning to a deployed, interactive prediction dashboard.

Unlike a rule-based scoring system, this model **learns patterns directly from data**, using measurable indicators of a business's digital maturity to estimate how promising a lead is for automation-focused outreach.

---

## 🚀 Highlights

* 🧹 End-to-end data cleaning pipeline (handles inconsistent formatting, mixed data types)
* 🛠️ Custom feature engineering from raw, incomplete data
* 🔡 Categorical encoding for model compatibility
* 📏 Feature scaling for fair model treatment across variables
* 🌲 Random Forest classifier with class balancing for imbalanced categories
* 📊 Model evaluation via accuracy, precision, recall, F1-score, and 5-fold cross-validation
* 🔍 Feature importance analysis for model interpretability
* 💾 Serialized model and preprocessing artifacts for reuse
* 🖥️ Interactive Streamlit dashboard for live predictions

## 🧮 Methodology

### 1. Data Cleaning
The raw `Reviews Count` field contained mixed formats (e.g. `"1,800"`, `"45,000+"`, plain integers). These were standardized into clean integer values before use.

### 2. Feature Engineering
A new binary feature, `Has_Social_Media`, was derived from the raw social media links column — converting sparse, high-cardinality text data into a simple, model-friendly signal.

### 3. Feature Selection
The model uses five features, chosen for their direct business relevance to automation readiness:

| Feature              | Rationale                                              |
| ---------------------- | ------------------------------------------------------- |
| Website Available      | Indicates existing digital presence                     |
| Automation Status       | Reflects current level of order automation               |
| Google Rating           | Signals business credibility and customer trust          |
| Reviews Count            | Indicates business popularity and establishment          |
| Has_Social_Media         | Reflects general digital engagement                       |

Identifier columns (name, address, phone) and outcome-dependent columns (call status, follow-up date) were deliberately excluded to avoid noise and data leakage.

### 4. Encoding & Scaling
Categorical fields were label-encoded, and all numeric features were standardized using `StandardScaler` to ensure no single feature dominates the model due to scale differences (e.g. review counts in the thousands vs. ratings on a 0–5 scale).

### 5. Model Training
A **Random Forest Classifier** (100 estimators) was selected for its strong performance on small tabular datasets and its resistance to overfitting compared to a single decision tree. `class_weight='balanced'` was applied to account for the underrepresented "Low" priority class.

### 6. Evaluation
The model was evaluated using an 80/20 stratified train-test split, followed by 5-fold cross-validation to obtain a more robust performance estimate.

## 📊 Results

| Metric                     | Value      |
| ---------------------------- | ------------ |
| Test Set Accuracy             | 60%          |
| Cross-Validation Average      | 56%          |
| Cross-Validation Range        | 30% – 80%    |

### Feature Importance

| Feature              | Importance |
| ---------------------- | ------------ |
| Reviews Count           | 36.9%        |
| Google Rating           | 25.0%        |
| Automation Status        | 23.1%        |
| Website Available         | 9.2%         |
| Has_Social_Media          | 5.8%         |

**Key insight:** Business popularity signals (review count and rating) were more predictive of lead priority than website availability alone — an interesting deviation from the original manual scoring assumption that website presence would dominate.

---

## ⚠️ Known Limitations

* **Small dataset (50 records):** Cross-validation scores ranged from 30% to 80% across folds, indicating the model's performance is sensitive to which examples fall into training vs. testing splits. This is a direct consequence of dataset size rather than model choice.
* **Class imbalance:** The "Low" priority class has only 9 examples in the full dataset, limiting the model's ability to learn robust patterns for that category.
* **No hyperparameter tuning performed** beyond class balancing — further gains may be possible with grid search, though the primary bottleneck remains data volume.

These limitations were identified deliberately through cross-validation analysis rather than left unexamined — the priority was understanding *why* performance was capped, not just reporting a single accuracy number.
